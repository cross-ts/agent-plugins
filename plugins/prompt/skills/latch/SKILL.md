# Latch

私は, 指示文書を候補間の振る舞い比較で改善し, 保持版を後退させる候補を採用しない. 隔離, 並列実行, 匿名化, 判定計算は, この SKILL.md と同じディレクトリの `scripts/` に任せ, 私は判断を要する部分を受け持つ. ファイル形式と隔離の仕組みは `scripts/README.md` にある.

## 実験ディレクトリ

私は実験を新しいディレクトリ(例: `latch-<対象名>/`)に作り, その外のファイルを作成も変更もしない. 対象の文書や資料は読むだけにし, 現行文書はフロントマターを含めてそのまま `variants/baseline_original.md` に複製し, その元のパスを `plan.json` の `source` に書く. 試行ごとに複製する作業環境は, 実験ディレクトリの `env/` に作る. `env/` には比較する文書を含めず, 文書が操作する外部の対象(tmux, Obsidian の Vault, 実リポジトリなど)は, 偽コマンドや複製で置き換える. 試行に要る環境変数と偽コマンドの置き場所は `plan.json` の `env_vars` と `path_prepend` に書き, CLI の設定ファイル(`.claude/settings.json`, `.codex/config.toml` など)を作って渡さない.

## 要件の行

私は, 既存文書があればその内容を, なければユーザーの要件を, 1行1要件で `p.tsv` に書き出す. 各行には適用条件, 様相(義務, 禁止, 許可), 強さ, 行為, 順序, 重大かどうかを書く. 重大とは, 1回の違反で候補を不採用にする行である.

## 境界ケース

私は候補を書く前に, 期待行動が条件で切り替わる箇所ごとに境界ケースを `cases.jsonl` に書く. 各ケースには入力, 行ごとの期待行動, 合否の証拠(ツール履歴, 成果物, 最終報告)を付け, 履歴や成果物で判定できる行は機械判定にする. ケースの入力は文書を名指しせず, 文書に従うかどうかで観察できる結果が変わる依頼にする. 禁止の行には違反を誘う入力を含め, 環境でも強制される禁止は試行と成否を別の行にする. 許可の行では, 許された行為を選ばなかったことを違反に数えない. 私はケースを select(4つ以上)と holdout に分け, holdout を候補の選定に使わない. 可能なら, 候補を読んでいない別セッションにケースを書かせる.

## 候補

私はラウンドを2段に分ける.

- 探索段: 同じ行を満たさせる方針が互いに異なる候補を4〜6個作る(手順を指定する, 完了状態だけを指定する, 義務と許可の境を示す, 条件と例外を示す, 対照用例を示す, など). 任意の2候補について体裁でなく方針の差を一文で言えるようにし, 箇条書き, 表, 見出しの違いだけの候補は調整段に回す. 例外を足すなど適用条件を変える候補は p の改版として扱い, 意図して変える行を `plan.json` の `changed_rows` に書き, その行の新しい期待行動をケースに足す.
- 調整段: 探索段で残った候補の行をすべて固定し, 表現だけを変える(発話内力, 丁寧さ, 明示の量). 強さを固定して言い回しを比べるラウンドと, 強さ自体を動かすラウンドは分ける.

私は候補ごとに, 狙う振る舞いの変化と, それを確かめるケースを実験ディレクトリの `hypotheses.md` に書く. `variants/` には比較する文書だけを置く. 強調表現は p に含まれる分を超えて加えない. 候補ごとに各行を表した文を `trace.tsv` に引用し, 準備のうちに `scripts/check_trace.py` を通るまで直す. 意味が保たれているかは自分で確かめる. `variants/` には候補のほか, 対照として現行文書の原文(`baseline_original`)と文書なし(`baseline_none`)を置く. 候補が差分なら, 現行全体と差分を組み込んだ全体を置き, regression ケースで比べる.

## 事前登録

私は実行前に `plan.json` を書き, 結果を見てから変えない. 決めるのは, 通常の行で拒否する低下幅, select と holdout の両方で求める最小改善幅, 意図して変える行の合格率, 反復回数(3以上), 追加試行の上限, モデル, 推論強度(Luna は high を主条件とする)である. 文書は各 CLI が普段読み込む位置(`CLAUDE.md`, `AGENTS.md`, スキルのディレクトリなど)に置く. 同じ時点で, 私は `results.md` に採否の規則を文章で書く: 重大な行の違反は1回で拒否すること, 通常の行の後退は許容幅で判定すること, 両モデルで後退がなく少なくとも一方で最小改善幅以上の改善が holdout でも再現した候補だけを採用すること, 同点や判定不能は保持版を据え置くこと, 採用した候補をそのファイルのまま `variants/` に残し, 次ラウンドの `--held` に渡して保持版にすること.

## 実行と判定

私は実験ディレクトリの `run.sh` に `"$SKILL_DIR/scripts/latch.sh" . --held <保持版>` を書く. `SKILL_DIR` はこの SKILL.md のあるディレクトリの絶対パスであり, 初回の保持版は `baseline_original`, 以降は前ラウンドで採用した候補である. `run.sh` は準備を終えた実験ディレクトリでそのまま最後まで動くように書き, 手作業の前提や, 前提が欠けたときに止める確認を置かない. 準備中に作れなかったものは `plan.json` の項目や `env/` の偽コマンドで代わりに用意し, それでも用意できなければ最終報告に書く. `latch.sh` は trace の確認, 実CLIでの混入確認, 試行, 採点, 判定を順に行う. 判定が保留なら, 表示された追加試行を保持版と候補に同じ数だけ足して判定し直し, 上限でも比較が揃わなければ保持版を据え置く.

## 次ラウンドと報告

採用した候補を保持版とし, 私は次に動かす1軸とその理由を `results.md` に書く. 改善が止まるか予算に達したら終了する. 最終報告には, 作成したファイルの一覧, `run.sh` の起動方法, まだ行っていない工程(試行, 採点, 判定)を書く.
